# Допущения и трактовки требований

Здесь собраны решения, принятые там, где техническое задание допускает разные трактовки или противоречит само себе. Каждое решение выбрано по правилу из раздела 26 ТЗ: простое и надежное, без изменения бизнес-требований.

## Противоречия в ТЗ

| № | Противоречие | Решение |
|---|---|---|
| A-1 | Раздел 2: PostgreSQL 18; раздел 17: «postgres (PostgreSQL 16)». | Используется **PostgreSQL 18** (стек из раздела 2 приоритетнее). Том смонтирован в `/var/lib/postgresql`, как требует образ `postgres:18`. Код не использует ничего специфичного для 18: с образом `postgres:16` система тоже работает, если смонтировать том в `/var/lib/postgresql/data`. |
| A-2 | Раздел 11: `GET /incoming` доступен «всем ролям»; раздел 4: у администратора в матрице нет просмотра карточек. При этом только администратор удаляет карточки. | Администратор получил одно разрешение **`document:view`**: список, карточка, поиск по номеру, история. Без него он не может убедиться, что удаляет именно дубликат или ошибочную запись. Поиск и фильтры (`document:search`), редактирование, резолюции, файлы, отчеты и выгрузка администратору недоступны. |
| A-3 | Раздел 4: делопроизводитель аннулирует ошибочную запись сменой статуса; раздел 6: переход «любой статус → зарегистрирован» — только администратор. | Переходы берутся из явной таблицы раздела 6: **аннулирование (возврат в «зарегистрирован») выполняет администратор**. Делопроизводитель исправляет ошибочную регистрацию редактированием карточки (разрешено до архивирования). Если запись нужно вернуть в начало цикла или удалить, он обращается к администратору. |
| A-4 | Раздел 6: «на рассмотрении → на исполнении (руководитель при создании резолюции)», но в матрице у руководителя нет права «смена статуса». | Переход выполняется **автоматически при создании первой резолюции** и записывается в историю от имени руководителя. Эндпоинт `POST /incoming/{id}/status` руководителю недоступен (403). |

## Бизнес-правила, уточненные при реализации

| № | Вопрос | Решение |
|---|---|---|
| B-1 | Формат номера | `REG_NUMBER_TEMPLATE`, по умолчанию `ВХ-{YYYY}-{NNNNNN}`. Плейсхолдеры: `{YYYY}`, `{YY}`, `{N…}` (ширина с ведущими нулями; больший номер не обрезается). Если в шаблоне есть год, счетчик ведется отдельно для каждого года, иначе нумерация сквозная. Шаблон без `{N…}` отклоняется при старте. |
| B-2 | Атомарность номера | Таблица `registration_counters` и `INSERT … ON CONFLICT DO UPDATE … RETURNING` в транзакции регистрации. Пропусков при откате нет. Номера удаленных карточек повторно не выдаются. Дополнительная защита — `UNIQUE` в БД. |
| B-3 | Дата регистрации и «сегодня» | Считаются в часовом поясе организации `APP_TIMEZONE` (по умолчанию `Europe/Moscow`, судя по реквизиту ИНН). Иначе документ, зарегистрированный в 00:00–03:00 по местному времени, получил бы вчерашнюю дату по UTC. Моменты времени (`created_at` и т. п.) хранятся как `timestamptz`. |
| B-4 | Дата поступления | `received_date` не может быть позже даты регистрации (422). |
| B-5 | Порог предупреждения о сроке | `DEADLINE_WARNING_DAYS` (по умолчанию 3). Состояния: `ok`; `warning` — до срока осталось от 0 до N дней включительно; `overdue` — срок прошел, документ не закрыт; `closed` — статусы «исполнен», «снят с контроля», «в архиве». Срок, наступающий сегодня, еще не считается просрочкой. |
| B-6 | Отметка исполнения при нескольких резолюциях | Исполнитель закрывает только свои резолюции. Документ становится «исполнен», когда закрыта последняя резолюция. Повторная отметка возвращает 409. |
| B-7 | Редактирование резолюции «до завершения процесса» | Разрешено, пока резолюция «на исполнении», а документ «на рассмотрении» или «на исполнении». Новым исполнителем может быть только активный пользователь с ролью `executor`. Срок резолюции не может быть раньше даты регистрации документа. |
| B-8 | Когда можно создать резолюцию | Документ должен быть «на рассмотрении» (первая резолюция) или «на исполнении» (дополнительные исполнители). Иначе — 409 `INVALID_DOCUMENT_STATE`. |
| B-9 | Поиск для исполнителя | Поиск и фильтрация по матрице исполнителю недоступны. Он получает список только своих поручений (`GET /incoming` без фильтров, с пагинацией и сортировкой). Запрос с фильтрами возвращает 403. |
| B-10 | Кто видит файлы и историю | Все, кто может просматривать карточку. Исполнитель видит только карточки со своими резолюциями, и в карточке ему показываются только его резолюции. |
| B-11 | Загрузка файлов | Делопроизводитель — в любом статусе, кроме «в архиве»; тип по умолчанию `source_scan`. Исполнитель — к своим документам «на исполнении» или «исполнен»; тип по умолчанию `execution_report`; загрузить `source_scan` он не может. |
| B-12 | Скан при регистрации | Регистрация принимает JSON, скан прикрепляется вторым запросом `POST /incoming/{id}/files`. Так остается строгая JSON-схема регистрации, а файл проходит те же проверки, что и остальные вложения. |
| B-13 | Проверка файла | Проверяются расширение (PDF, JPG/JPEG, PNG, DOCX), MIME от клиента, сигнатура начала файла и размер. Исходное имя очищается от путей и управляющих символов и используется только для отображения. Ключ хранения — `documents/<id>/<uuid>.<ext>`. |
| B-14 | Скачивание | Потоковый ответ через backend (второй разрешенный ТЗ вариант). MinIO не нужно публиковать наружу, и RBAC проверяется при каждом скачивании. |
| B-15 | Удаление файла | Не реализовано: в ТЗ помечено как необязательное. |
| B-16 | `GET /reports/{id}/download` | Не реализован (в ТЗ опционален): `POST /reports/generate` сразу возвращает PDF, и хранить отчеты не требуется. |
| B-17 | Период отчетов и выгрузки | Период отбирается **по дате регистрации**. |
| B-18 | Показатели отчета по исполнителям | Единица учета — резолюция. Средний срок исполнения = `executed_at − created_at` резолюции в днях. Резолюция считается просроченной, если исполнена после срока или не исполнена, а срок прошел. Процент просрочки = просроченные / все резолюции исполнителя. |
| B-19 | Отчет по срокам | Фактическая дата исполнения — дата перехода документа в «исполнен» по истории. Отклонение = факт − срок (со знаком). |
| B-20 | CSV | UTF-8 с BOM, разделитель `;`, окончания строк CRLF. Значения, начинающиеся с `= + - @`, экранируются апострофом, чтобы Excel не выполнял их как формулы. |
| B-21 | Logout | JWT без состояния: выход — удаление токена на клиенте. Черный список не реализован (в ТЗ опционален). Деактивация пользователя блокирует его токены сразу. |
| B-22 | Ответ на вход деактивированного пользователя | 403 `USER_INACTIVE`, только при верном пароле. При неверном пароле всегда 401, поэтому нельзя узнать, существует ли учетная запись. |
| B-23 | Ограничения для администратора | Нельзя деактивировать себя и снять с себя роль администратора (409), чтобы система не осталась без администратора. |
| B-24 | Корреспондент | Обязательно только наименование. ИНН (10 или 12 цифр) необязателен, потому что корреспондентом может быть гражданин. |
| B-25 | Типы документов | Выведенный из использования тип (`is_active = false`) нельзя выбрать для новой регистрации. Старые карточки его сохраняют. |
| B-26 | Должность пользователя | Необязательна; подразделение обязательно (по составу полей в разделе 10). |
| B-27 | Поиск по ключевым словам | `ILIKE` по краткому содержанию, адресату, номеру и наименованию корреспондента, без учета регистра, со спецсимволами LIKE, экранированными. Для `summary` создан GIN-индекс `pg_trgm`. Регистронезависимость для кириллицы опирается на UTF-8 локаль кластера (в образе `postgres` по умолчанию `en_US.utf8`). |
| B-28 | Дополнительный фильтр | `GET /incoming?deadline_state=overdue|warning` — отбор просроченных и близких к сроку документов для контроля сроков. |
| B-29 | Имя столбца `metadata` | В ORM атрибут называется `meta`, потому что имя `metadata` зарезервировано в SQLAlchemy. Столбец в БД и поле API называются `metadata`, как в ТЗ. |
| B-30 | Порядок истории | Кроме `created_at` есть столбец `seq` (IDENTITY), чтобы записи одной транзакции шли в порядке их создания. |

## Инфраструктура

| № | Вопрос | Решение |
|---|---|---|
| C-1 | Хранение токена | Заголовок `Authorization: Bearer <token>`. В Swagger UI — кнопка **Authorize**. |
| C-2 | Миграции | Применяются при старте контейнера backend (`scripts/entrypoint.sh`). Их можно запустить и вручную: `docker compose exec backend alembic upgrade head`. |
| C-3 | Seed | Запускается вручную (`python -m scripts.seed`). Скрипт идемпотентен: если в БД уже есть пользователи, он ничего не делает. Все персональные данные вымышлены. История в seed соответствует статусам документов, что проверяет тест. |
| C-4 | Образы MinIO | Используются `minio/minio:latest` и `minio/mc:latest`. MinIO прекратил регулярную публикацию образов community-редакции. Для воспроизводимости рекомендуется закрепить конкретный тег `RELEASE.*`, проверенный в вашей среде, или заменить сервис другим S3-совместимым хранилищем: backend работает с любым S3 API. |
| C-5 | Сборка под Python 3.14 | Wheel-пакеты собираются в отдельной стадии Dockerfile с компилятором. Итоговый образ компилятора не содержит. |
| C-6 | Тесты | Интеграционные тесты используют отдельную БД `<POSTGRES_DB>_test` и бакет `correspondence-test`, поэтому рабочие данные не затрагиваются. Перед тестами миграции прогоняются вниз и вверх (проверяются `upgrade` и `downgrade`). |
| C-7 | Бэкап файлов | `mc mirror` в контейнере `minio/mc`. Адрес с учетными данными передается переменной окружения `MC_HOST_src`, поэтому ключи S3 должны состоять из URL-безопасных символов (латиница, цифры). |
| C-8 | Размер загрузки | Файл читается в память целиком (не больше `MAX_UPLOAD_SIZE_MB + 1 байт`). При лимите 20 МБ это приемлемо и упрощает проверку сигнатуры и размера. |
